## The traps
1. Breaking the live demo. Render rebuilds the Phase 0 static site from main with "npm ci && npm run build" → ./dist on every merge. If `build` starts requiring Postgres, env vars or the server compile to succeed, or if dist/ changes shape, the public demo breaks on merge. Prove the static build is unchanged: run `npm ci && npm run build` with no env vars set and compare the dist/ file list before and after your change.
2. Database tests that silently skip. A suite that skips when DATABASE_URL is missing is green and worthless in CI. Make absence a hard failure with a message. Prove it by showing the failure output once with DATABASE_URL unset, and say so.
3. Damaging the operator's Postgres. It's a shared local server with other projects' databases. Only CREATE and DROP databases you named yourself with a unique prefix (for example `supa_test_<random>`). Never drop by pattern, never touch roles, never touch an existing database. Report every database you created and confirm it was dropped.
4. Logging secrets. Fastify's default request logging includes headers. With auth arriving in later tasks, redaction must be in place now and tested, not added later.
