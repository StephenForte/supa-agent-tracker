## Outcomes
1. **Routes** (all `requireUser` → `UserAccess { kind:'user', userId: request.user.userId }`; collections paginate per docs/api.md; every mutation takes `request_id` and goes through `withIdempotency` with the supplied `tx`; existing-resource mutations take `expected_revision`):
   - GET /api/account → `{ id, name, email, emailVerified }` for the signed-in user (from `users`).
   - GET /api/projects?include_archived=true|false&cursor&limit: the user's projects in the repo's order. Archived projects are hidden unless `include_archived=true`. Add that option to server/repo/projects.ts `listProjects`.
   - POST /api/projects (a ProjectInput body plus request_id) → 201 with the Project.
   - GET /api/projects/:projectId.
   - PATCH /api/projects/:projectId (a partial ProjectInput plus expected_revision and request_id).
   - GET /api/agents?project_id=&cursor&limit: one project's agents, or every agent across the user's projects when project_id is omitted.
   - GET /api/runs?project_id=&cursor&limit: runs for one project or across all the user's projects. Each item includes prReferences, tools (null when absent), childRunIds and parentRunId, but **no events** (D-026).
   - GET /api/runs/:runId → the full `Run`, events included (oldest first). The project is resolved from the run through the user's access, never from client input.
   - PATCH /api/runs/:runId (a RunMetadataPatch plus expected_revision and request_id): metadata correction only. It never changes execution state, and it never advances last_contact_at (the repo already preserves it for users).
   - POST /api/runs/:runId/close {outcome: failed|cancelled, reason, expected_revision, request_id}: manual close of a **running** execution. The repo selects manual_close and appends the audit event. The reason becomes the event message. Next steps are never touched. Closing an ended run → 409 `conflict` with the current run, or 400 `validation_error` (pick one and document it).
   Another user's project, agent or run → 404 `not_found`, and nothing changes.
2. **Cross-project reads** live in server/repo/views.ts:
   - account by user;
   - agents across the user's projects;
   - run pages across the user's projects;
   - run lookup by id for a user.
   Each takes `UserAccess`, filters by `projects.owner_id = userId` inside the query, and uses keyset pagination with a stable order. It is data access only; HTTP stays in server/api/**.
3. **Field mapping.** The DB's flat `stale_threshold_minutes`, `heartbeat_expected` and `reporting_instructions` map to and from `reportingPolicy { staleThresholdMinutes, heartbeatExpected, instructions }`. Event actors map to `RunEvent.actorId` (the user or credential id). Timestamps are UTC ISO-8601 strings.
4. **Input validation** with zod: bounded string lengths and tag counts; enum values per src/domain/types.ts; stale threshold a positive integer. Every URL field (`repositoryUrl`, `prdUrl`, PR reference `url`) must be absolute `http:` or `https:`; anything else is `validation_error`.
5. **docs/api.md** gains a "Projects, agents and runs" section: routes, bodies, caps, the include_archived rule, the D-026 events rule and the manual-close rule. server/README.md gains a "User API (P1-C2)" section.
6. **Tests** (server project, real Postgres scratch databases, `app.inject` with the `x-test-user-id` seam) prove properties, not just happy paths:
   - Isolation: with users A and B, every route B calls against A's ids returns 404, and a snapshot of every table is identical before and after. The cross-project lists for B never contain A's agents or runs.
   - Archived projects are hidden by default and shown with include_archived=true.
   - Revision conflict → 409 with `error.details.current` and no change. A replayed request_id returns the original response; a different body gets idempotency_mismatch.
   - Manual close of a running run → execution failed/cancelled, finished_at set, one manual_close event, one audit event, next steps unchanged. A close of an ended run is refused and changes nothing.
   - A metadata PATCH leaves last_contact_at and execution_state unchanged.
   - List items carry no `events`; detail carries them in order.
   - `javascript:alert(1)` as repositoryUrl, prdUrl or a PR url → 400.
   - Pagination: three pages over 2×limit+1 runs return every run exactly once.

## The traps
1. **Resolving the project from the client.** `GET /api/runs/:runId` has no project in the path. If the handler takes a `project_id` query or body value and passes it to the repo, the run's real project goes unchecked. Resolve run → project inside an owner-filtered query (views.ts), then call the project-scoped repos. Consequence: one user reads another's runs by guessing ids, which fails the PRD's first acceptance scenario.
2. **Stored links that execute.** The web app renders repositoryUrl, prdUrl and PR urls as anchors. A `javascript:` or `data:` URL stored here becomes a click-to-run script in the owner's browser. Reject non-http(s) at the API, not only in the UI.
3. **Unbounded list payloads.** Heartbeats append an event every few minutes and history is never purged. Lists that embed events grow without limit and P1-E polls every 5–10 s. Lists omit events (D-026); detail carries them.
4. **Touching the operator's other databases.** Only your own `supa_test_*` scratch databases.
