## Outcomes
1. **0002_auth.sql** adds the tables better-auth needs (sessions, accounts, verification; plus rate-limit storage if you choose database storage) with text ids and timestamptz. better-auth maps onto the existing `users` table: name → display_name, emailVerified → email_verified, plus created_at/updated_at; timezone stays a user field. You may add columns to `users` additively (for example a nullable `image` if the adapter requires one). Do not rename or drop anything in 0001. Append the matching Drizzle definitions to server/db/schema.ts; the existing drift test must pass unchanged, covering your tables too. FKs to users use RESTRICT, not CASCADE. 0001's no-cascade test must stay green.
2. **Registration is invite-only.** Sign-up succeeds only for an email on `REGISTRATION_ALLOWLIST` (case-insensitive, trimmed). Any other email gets 403 `forbidden` with the message "Registration is by invitation only", and no user row is created. An allowlisted sign-up creates an unverified user and sends a verification email. Login is refused until the email is verified.
3. **Login, logout, sessions.** Secure session cookies: HttpOnly, SameSite=Lax, and Secure when PUBLIC_URL is https. Sessions expire after a fixed lifetime, which you choose and document. Logout and server-side revocation make the cookie stop working on the next request. A user can list and revoke their own sessions. A password change revokes the user's other sessions.
4. **Password reset**: the request always returns the same generic response, whether or not the account exists. The link is single-use and expires (1 hour). Using it sets the new password and revokes existing sessions.
5. **CSRF**: state-changing auth and `/api` requests from an origin other than PUBLIC_URL are rejected. Use better-auth's trusted-origins check plus SameSite cookies, or an equivalent. Prove it with a test.
6. **Login rate limiting**: repeated failed sign-ins for one email or IP get 429 with a stable JSON error code `rate_limited`. Add that code to server/app/errors.ts and docs/api.md. State the limit and window in server/README.md.
7. **Email interface** in server/email/**: `sendEmail({to, subject, text, html?})`, with two implementations:
   - console: logs to stdout in dev and captures in memory in tests;
   - Resend: `fetch`, key from env, never logged.
   Config selects one. Verification and reset emails link to `${PUBLIC_URL}` paths that exist in the web app's route table; if a needed page doesn't exist, use the closest existing path and list the gap in RESIDUAL GAPS.
8. **Real `requireUser`** in server/app/auth-context.ts: resolves the better-auth session from the request cookies and sets `request.user = { userId }`; with no valid session it returns 401 `unauthenticated`. **Keep the existing `x-test-user-id` path working only when NODE_ENV=test**, so other wave-3 tasks' route tests keep passing, and add a test proving that header is ignored under development and production.
9. **Auth routes** live under `/api/auth/*` (better-auth's handler bridged into Fastify) and must coexist with the existing `/api` JSON 404 handler. Unknown `/api/auth/...` paths still return JSON, never HTML.
10. **No secrets in logs.** Passwords, reset or verification tokens, session tokens, BETTER_AUTH_SECRET and RESEND_API_KEY never reach logs or error bodies. Test this by capturing the production logger during a sign-up, login, reset request and reset completion, then asserting none of the submitted secrets appear in the captured output.
11. **config.ts** parses the new env vars with the same error style (names the variable, never prints the value). The process refuses to start outside test with BETTER_AUTH_SECRET missing or shorter than 32 characters, or with EMAIL_PROVIDER=resend and no key or sender.
12. **Tests** (server project, real Postgres scratch databases via server/test/database.ts) cover outcomes 2–11 through HTTP using `app.inject`, including:
   - a non-allowlisted sign-up creates no row;
   - an unverified login is refused;
   - a used or expired reset link fails;
   - a revoked session gets 401 on the next request;
   - a cross-origin POST is rejected.

## The traps
1. **Logging the body.** Auth bodies hold passwords and tokens. Fastify's logger, better-auth's own logger, or an error handler echoing input can each leak them. The request logger already redacts headers (docs/api.md "Bodies and logs"). Keep it that way, and keep better-auth's logger quiet or redacted. Consequence: a password in Render's log store, which can't be recalled.
2. **Breaking every other task's tests.** P1-C1 and P1-D test their browser routes with `x-test-user-id` under NODE_ENV=test. If the real `requireUser` drops that seam, their suites go red the moment you merge. Keep the seam, test-only.
3. **Account enumeration.** Reset and "resend verification" must answer identically for known and unknown emails. Registration may say "by invitation only", but it must not reveal whether an allowlisted address already has an account.
4. **Auth tables that fight the drift test.** Hand-written SQL and Drizzle must match exactly. If better-auth's generator proposes a schema, translate it into 0002 by hand and keep schema.ts in lockstep. Don't let it migrate on its own.
5. **Touching the operator's other databases.** Only create and drop your own `supa_test_*` databases through the existing helper.
