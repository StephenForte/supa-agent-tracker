## The trap
**Double idempotency.** The registrar's `mutate = true` path already wraps the handler in `withIdempotency` (server/mcp/registry.ts). Every agent-steps mutation **also** wraps itself in `withIdempotency` with the same actor scope and request_id (`mutate()` in server/steps/agent-steps.ts). Registering the step mutations with `mutate = true` nests the two. The inner call stores the key row, then the outer call inserts the same `(scope, request_id)` primary key, the transaction fails, and every step write becomes `internal_error`. The fix must keep exactly one idempotency layer: register the step tools with `mutate = false` and let agent-steps own it. Then map its `idempotency_mismatch` result as in outcome 2. Don't strip idempotency out of agent-steps (its HTTP-independent tests depend on it). The retry test in outcome 4 is what proves you got this right: it fails under either double wrapping or no wrapping.

Secondary: **logic creeping into the tool layer.** If you find yourself re-checking authorship, revisions or scope in step-tools.ts, stop. That belongs in agent-steps and is already there. A second copy drifts.
