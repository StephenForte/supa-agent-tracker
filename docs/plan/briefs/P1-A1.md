# P1-A1 — Remote MCP client compatibility research + probe server

Phase 1 adds a remote MCP endpoint that coding agents and bots use to report runs. The PRD requires per-user, project-scoped, revocable access tokens sent in an Authorization header, but warns that this is "a product requirement, not evidence that each client accepts manually entered bearer headers" and that "OAuth may be required." Three initial clients must work: Cursor, Claude Desktop on macOS, and Grok Bot (https://x.ai/bot). Your job is to find out, with evidence, what each one supports, and to build a tiny probe server the operator can point each client at to confirm it live. The answers decide the Phase 1 auth design (D-017). A confident wrong cell in your matrix becomes a wrong architecture, so "unknown — needs live test" is a good answer when the evidence isn't there.

3. spike/mcp-probe/: a minimal remote MCP server for the live test (P1-A2). Requirements:
   - Own package.json and lockfile inside spike/mcp-probe/. Use the official MCP TypeScript SDK at its current release, on Node 24. A README states the exact SDK version used.
   - Speaks Streamable HTTP at /mcp. Also serves the deprecated HTTP+SSE transport only if your research shows a target client needs it.
   - Auth: if env PROBE_TOKEN is set, requests must carry "Authorization: Bearer <PROBE_TOKEN>" or get a 401 that follows the MCP spec's authorization error shape. If PROBE_TOKEN is unset, it runs authless, so a client that can't send headers can still be observed connecting. Never log the token value. Log only whether an Authorization header was present and whether it matched.
   - If research shows a target client needs OAuth discovery to even attempt a connection, serve the spec's protected-resource metadata so the probe can record how far that client gets. Do **not** build an authorization server; that's a Phase 1 design decision. Record the gap.
   - Tools:
     - probe_whoami: returns what the server observed about this session: protocol version, clientInfo from initialize, transport, whether auth was present and valid, and request headers with any Authorization value redacted.
     - probe_check_in(project_id, agent_name, title, workload_type, harness?, model?): echoes the input with a fake run_id. It shows whether the client's model fills fields such as harness and model honestly.
     - probe_heartbeat(run_id): returns a server timestamp.
   - Keeps an in-memory, bounded log of the last 200 calls (tool, timestamp, clientInfo, auth present yes/no; no argument values beyond the tool's own fields; nothing secret). A GET /probe/log endpoint returns that log only when the bearer token is valid (or always in authless mode), so the operator can read results after each client test.
   - Binds to the PORT env var (Render convention), defaulting to 8787 locally.
   - Automated tests using the SDK's own client over Streamable HTTP against a server started in the test: initialize, list tools, call each tool; 401 without a token when PROBE_TOKEN is set; success with it; authless mode works; the log never contains the token string.
   - README: run locally; the exact Render settings for a later manual deploy (web service, name supa-mcp-probe, root dir spike/mcp-probe, build/start commands, env PROBE_TOKEN, health path); and how to read /probe/log.

## The traps
1. Asserting support from memory or marketing pages. Client MCP features changed repeatedly through 2025–2026, and a remembered "Claude Desktop accepts custom headers" or "Cursor supports OAuth" may be out of date or wrong. Consequence: Phase 1 builds the wrong auth path and the integration fails at P1-F after weeks of work. Cite current vendor docs with dates. If docs and behaviour might differ, mark the cell "unknown — needs live test".
2. Breaking the app's CI with the spike. The root eslint config lints every **/*.ts file, and root Vitest picks up every *.test.ts file in the repo. Without changes, spike files run under the app's jsdom test environment without their dependencies installed, and CI fails. Exclude spike/** from the root ESLint config and the root Vitest config (the only root config edits allowed). Then add a separate CI job that runs npm ci and npm test inside spike/mcp-probe. Prove both: the root gate passes with the same 22 files / 221 tests, and the spike job passes.
3. Touching the root render.yaml. It's a synced Render Blueprint: any service added there is created automatically on merge, which deploys the probe without approval. The probe's deploy settings live only in spike/mcp-probe/README.md.
4. Leaking the probe token. It's a real credential once deployed. Tests generate a random token at runtime; nothing token-like is committed, logged or echoed back by probe_whoami.
