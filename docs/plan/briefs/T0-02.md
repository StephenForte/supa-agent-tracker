# T0-02 — Projects dashboard and project create/edit form

This is the screen a user lands on after time away. In seconds they must see which projects have live work, which need review, what finished, and the first human step on each. Accuracy of the counts matters more than visual flourish.

## Line of work
Branch t0-02-dashboard from the current tip of main. PR title: "T0-02: Projects dashboard and project form". Identifiers are pre-assigned; if one looks wrong, stop and ask rather than pick another.

## Outcomes
1. /projects (src/pages/projects/ProjectsPage.tsx) renders a card per project with: name (link to /projects/:id), description, project type, lifecycle, tags; repository name/link and PRD link when present (no empty link chrome when null); live-running, stale-running and review-needed counts plus total logical agents and total runs (all from projectCounts); latest update = agent name, message and time (latestActivity + agent lookup by agentId); and the two slot components exactly as provided: NextStepsPreview and PrivateNotePreview from src/features/next-steps and src/features/private-notes. Those bodies are T0-04's and are placeholders today; render them, don't reimplement them.
2. Default order is active-first via compareProjectsActiveFirst. Alternate sorts: latest activity, name, created date. Archived projects are hidden by default and shown through the lifecycle filter.
3. Filters that compose and clear together: text (name, description, tags, repo), lifecycle, project type, activity (live / stale / review-needed / blocked work), harness (from the project's runs; null harness = "Unknown"), tags. One "Clear filters" action. A no-match state names the active filters and offers to clear them. A true empty state (no projects) offers "Create a project".
4. Demonstrable states: /projects?demo=loading, ?demo=error and ?demo=empty render the loading, error and empty states without changing store data (D-015). Normal operation uses useSourceQuery's real states.
5. /projects/new and /projects/:projectId/edit (src/pages/projects/ProjectFormPage.tsx): fields for name, description, type, lifecycle, repository name, repository URL, PRD URL, tags, stale threshold minutes, heartbeat expected, reporting instructions. Create uses createProject; edit uses updateProject with the project's revision. Typed results: invalid → field-level or summary message; conflict → tell the user the project changed elsewhere, show the current values, keep their draft, and offer to apply their draft on the new revision. Never overwrite silently. Cancel returns without changes. Success navigates to the project's detail page. Headings stay "New project" / "Edit project".
6. Cards: the whole card may be clickable, but repo/PRD/latest-update links inside it open only their own target. Long names wrap (prj_dashboard). Missing links stay usable (prj_weather).

## The trap
Counting a finished run that is "Waiting for review" as running, or counting stale runs as live. Running counts include only live Running executions (PRD "Execution state, work status, and liveness"). run_3 is Finished + Waiting for review and must never show as running. run_4 is running but stale and must show as stale, not live. If cards and the T0-03 detail header disagree, the return-from-break workflow is broken. projectCounts already encodes this; use it and add nothing on top.

## Must hold

- Filters never hide a project's live work silently. The active filter set is always visible.
- Card rendering reads private-note content only through PrivateNotePreview, never directly.
