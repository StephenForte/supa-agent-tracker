These screens show the intended account and token lifecycle without collecting anything real. Two things must be impossible: mistaking a demo token for a live credential, and reading an unverified setup snippet as working instructions.

2. Account settings (/settings): demo identity from getAccount (name, email, verified), password change and session management shown as disabled demo affordances with honest copy. Navigation between the three settings sections.
3. MCP tokens (/settings/tokens): list from listTokens with label, scopes (project names), created, last used ("Never" when null), status (Active / Revoked) and the masked display value. Create dialog: label plus project-scope checkboxes → createToken. The plaintext is shown once in a reveal panel with Copy (navigator.clipboard; on failure, select the text and show an error message) and a prominent "Fake demo token — cannot authenticate anything". Dismissing the panel or navigating away discards the plaintext for good. Revoke (confirm) → revokeToken. Rotate (confirm) → rotateToken, which reveals the new plaintext once and shows the old token as revoked. Invalid result → message. Empty state when no tokens exist.
4. Integration setup (/settings/integrations): one card each for Cursor, Claude Desktop (macOS) and Grok Bot, each with status "Not connected · Not tested". Each card has a configuration example built only from obvious placeholders (<MCP_SERVER_URL>, <YOUR_TOKEN>, etc.) under an "Unverified — not a working configuration" label. No install commands, CLI invocations or claims of compatibility. A "Reporting protocol preview" with a project selector shows the PRD base instruction draft plus that project's agent-facing context: project id and name, reporting policy, open next steps and waiting note. Build it only from TrackerDataSource.

## The trap
A plaintext token outliving its one-time reveal. It ends up in component state that survives navigation, a URL, the console, localStorage or sessionStorage, or a test snapshot. The data layer never stores plaintext; your view must not either. Keep it in transient state that is cleared on dismiss and on unmount. Add a test: create a token, dismiss the reveal, and assert the plaintext no longer appears anywhere in the document, and that localStorage and sessionStorage contain no "sat_demo_NOT_A_REAL_TOKEN" substring.

Second trap: the reporting preview leaking private notes. Test it by rendering the integrations screen with a PrivateNotesSource whose methods throw, selecting prj_offers and prj_dashboard, and asserting the preview renders and contains neither seeded private-note text.

## Must hold
- No form submission or network request on any auth screen. No password value ever reaches React state.
- A token's plaintext appears only in the reveal panel, only once.
- Integration status is never anything other than "Not connected · Not tested" in Phase 0.
