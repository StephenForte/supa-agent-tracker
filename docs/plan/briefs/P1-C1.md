## Outcomes
1. **Token REST** (all `requireUser`; bodies use `request_id`/`expected_revision` per docs/api.md; responses use the `McpToken` field names):
   - GET /api/tokens: the user's tokens, never a hash.
   - POST /api/tokens {label, project_ids, request_id} → `{ token, plaintext }`. The plaintext appears in this response only.
   - POST /api/tokens/:id/rotate {request_id, expected_revision}: revokes the old token and issues a new one with the same label and scope, in one transaction. Returns `{ token, plaintext }`.
   - POST /api/tokens/:id/revoke {request_id, expected_revision}: revoked tokens fail on the very next MCP request.
   - Scope edits and label edits are not required.
2. **Bearer authentication** replaces the `requireMcpCredential` stub. The bearer is hashed, the credential looked up, revocation checked and stored grants loaded, producing a `CredentialAccess` (server/repo/access.ts). Add the trusted bootstrap lookup (hash → credential + grants, no prior access context) to server/repo/credentials.ts; it is the one place a hash is resolved without an access context. Extend `McpCredential` in auth-context.ts with `credentialId`. A missing, malformed, unknown or revoked token gets 401 with `WWW-Authenticate: Bearer resource_metadata="<PUBLIC_URL origin>/.well-known/oauth-protected-resource"`, plus `error="invalid_token"` when a token was presented. GET /.well-known/oauth-protected-resource returns RFC 9728 JSON for the resource. Tokens in a URL query are never accepted.
3. **Last-used bookkeeping must not make the owner's edits conflict.** Update `last_used_at` at most once a minute per credential, **without bumping the credential's revision**. Add that function to server/repo/credentials.ts. As written, `touchCredential` bumps the revision on every call, so a busy agent would make every revoke/rotate from the settings page a 409.
4. **/mcp** speaks Streamable HTTP via the SDK. Choose stateless or session mode, justify it in the PR body, and remember Render runs one instance. Any request carrying an `Origin` header gets 403 JSON before tool dispatch (the agent clients connect server-to-server; this blocks browser/DNS-rebinding use). Expose the server name, a version and an `api_version` (start at "1") in server info and in get_project.
5. **Tools.** Every one uses the repositories with the request's `CredentialAccess`; authorization comes only from the credential, never from a client-supplied owner id. Mutations require `request_id` and go through `withIdempotency`, using the supplied `tx` for every repository call inside it.
   - list_projects: authorized summaries (repo listProjects), paginated.
   - get_project: metadata, open To Dos (next steps not done + waiting note), current running runs, the reporting policy (reporting_instructions, stale threshold, heartbeat_expected) and api_version.
   - check_in {project_id, agent_name, title, workload_type, task_id?, harness?, model?, parent_run_id?, external_execution_id?, request_id}: find-or-create the logical agent by (project, name), create the run, and store the observed MCP clientInfo and User-Agent as metadata only (D-018). Returns run_id, revision and the reporting policy. Replaying the same request_id returns the same run. Coding runs require task_id. Harness and model are never defaulted or inferred (p1-a2 consequence 4).
   - update_status {run_id, expected_revision, work_status?, message?, blocker?, completion_summary?, pr_references?, harness?, model?, request_id}: returns the new revision.
   - heartbeat {run_id, request_id}: advances last_contact_at and appends a heartbeat event, **without bumping the run revision** (D-024). Add that function to server/repo/runs.ts. Otherwise a hook-adapter heartbeat (P1-F) would turn the agent's next update_status into a conflict. A heartbeat for an ended run returns a stable error and never reopens it.
   - check_out {run_id, expected_revision, execution_state (finished|failed|cancelled), work_status, completion_summary?, pr_references?, no_pr_reason?, tools?, request_id}: ends the execution and sets finished_at; work may stay waiting_for_review or blocked. Coding runs require completion_summary. A coding run with no PR needs either pr_references or no_pr_reason.
   - record_tool_usage {run_id, tools: [...], request_id}: upserts aggregates; coverage defaults to self_reported. Absent rows stay "no telemetry".
   Conflicts return a structured tool error with code `conflict` and the current run (never a private note). Map not_found, forbidden, validation_error, idempotency_mismatch and rate_limited to the same stable codes as docs/api.md.
6. **Bounds and rate limit**: cap string lengths, PR references per call and tool rows per call; state the caps in docs/api.md. Rate-limit per credential, then 429 / `rate_limited`. A single-instance in-memory limiter is acceptable; state the limit and that it resets on restart.
7. **Private notes never leave through MCP.** No tool, error, conflict body or log line contains private-note text. Prove it with a seeded note and a scan of every tool response in the full-flow test.
8. **docs/api.md** gains an "MCP" section (endpoint, auth, 401 shape, tools with fields, errors, caps, rate limit, idempotency, heartbeat revision rule) and a "Tokens" section. server/README.md gains an "MCP and tokens (P1-C1)" section.
9. **Tests** (server project, real Postgres scratch databases). Issue a real token through the REST route (using the test `x-test-user-id` seam), then drive /mcp with the SDK's own client against the app listening on port 0. Cover:
   - Full flow: check_in → update_status → heartbeat → check_out. Revisions increase except on heartbeat. finished_at is set, and work_status waiting_for_review survives check-out.
   - A replayed check_in request_id returns the same run_id with no new rows. The same request_id with a different body gets idempotency_mismatch.
   - Scope: a token scoped to X gets not_found for project Y and for another user's project, including a parent_run_id taken from Y.
   - A revoked token gets 401 on the next call. A rotated token's old value gets 401, and its new value works.
   - Late heartbeat after check-out: error, run still ended.
   - Origin header → 403; no header / bad token → 401 with the WWW-Authenticate shape.
   - The plaintext token never appears in the database (scan every text/jsonb column, idempotency_keys.response included) or in captured logs.
   - Validation: a coding check_in without task_id, and a coding check_out without a summary, get validation_error.
   - Last-used updates don't bump the credential revision.

## The traps
1. **The idempotency table stores the plaintext token.** `withIdempotency` saves the response JSON so a replay can return it. If token issuance or rotation goes through it unchanged, `idempotency_keys.response` holds every issued token in plaintext forever. That breaks "hash-only, copy-once" and the PRD's "never plaintext tokens". Store a response without the plaintext. A replay returns the token metadata with `plaintext: null`, or a `replayed` marker, and the plaintext is never shown twice.
2. **Trusting `projectIds` from anywhere but the stored grants.** The access context narrows; it never widens (server/README.md). Build `CredentialAccess.projectIds` from the database at authentication, and never from tool input.
3. **Revision churn from liveness.** Heartbeats and last-used bookkeeping that bump revisions turn healthy traffic into 409s for the agent and for the owner. Both are pinned above. Don't let a helper that bumps revisions creep back in.
4. **Identity from connection metadata.** Grok presents as Cursor and subagents reuse the parent session (p1-a2-results). Harness, agent_name and parent_run_id come only from the check-in payload; clientInfo and User-Agent are stored, never used to decide anything.
5. **Touching the operator's other databases.** Only your own `supa_test_*` scratch databases.
