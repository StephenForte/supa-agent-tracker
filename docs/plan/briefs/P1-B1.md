# P1-B1 — Database schema (migration 0001) and the access-controlled data layer

This task creates the Phase 1 database: one SQL migration with the whole PRD data model, typed Drizzle definitions that match it, and a repository layer through which every later task reads and writes. The repository layer is where account isolation and token scopes are enforced, so the PRD's hardest promises live here:
- users never see each other's projects;
- an MCP token can only touch its scoped projects;
- private notes are unreachable from any agent path;
- history is never deleted.

Three workers build browser auth, the MCP endpoint and next steps on top of this, in parallel. A missing column or a leaky query here becomes three workarounds.

## Outcomes

1. **server/db/migrations/0001_initial.sql** creates the domain schema (Postgres 18, `timestamptz` everywhere, text or uuid ids, your choice and documented):
   - users: id, email (unique, case-insensitive), email_verified, display_name, timezone, created_at, updated_at. **Auth-library tables (sessions, accounts, verification tokens, invites) are not yours.** P1-B2 adds them in 0002 and maps better-auth onto this users table, so keep users minimal and name columns so a library adapter can map onto them.
   - projects: owner_id → users, name, description, type (coding|automation), lifecycle (active|paused|completed|archived), repository_name/url, prd_url, tags, stale_threshold_minutes (>0, default 15), heartbeat_expected, reporting_instructions, created/updated, revision.
   - logical agents: project_id, name, title, workload_type, created_at; unique (project_id, name).
   - runs, which are immutable identity with mutable state:
     - project_id, agent_id, task_id, title, workload_type
     - execution_state (running|finished|failed|cancelled) and work_status (in_progress|blocked|waiting_for_review|completed|failed|cancelled) as **separate** columns, with a check that finished_at is null exactly when execution_state = running
     - started_at, finished_at, last_contact_at, updated_at
     - harness and model (nullable, agent-reported)
     - observed_client_info (jsonb) and observed_user_agent (text), metadata only (D-018)
     - message, completion_summary, blocker, no_pr_reason
     - parent_run_id, external_execution_id, revision
   - run_events (append-only): run_id, kind (check_in|status|heartbeat|check_out|manual_close), received_at (server), occurred_at (client, nullable), actor (user or credential reference), message, execution_state and work_status at that point.
   - pull_request_refs per run: number, title, url, repository_name, primary flag; at most one primary per run.
   - tool_usage_aggregates per run and tool: name, source (mcp|native|shell|other), call_count, nullable success/failure counts, last_used_at, coverage (self_reported|adapter_captured). Absent rows mean "no telemetry", which is never the same as zero.
   - next_steps: project_id, position, instruction, done, source_run_id, completion_changed_by/at, created/updated, revision; plus one waiting_note per project (text, source_run_id, updated_at, revision).
   - **private_notes in their own table**: project_id unique, text, updated_at, revision. No foreign key or view links it into anything an agent path reads.
   - audit_events: actor, action, target, details jsonb, created_at (manual close, completion changes, token issue/revoke later).
   - mcp_credentials: user_id, label, **token_hash only** (unique), display suffix, created_at, last_used_at, revoked_at; plus mcp_credential_projects (credential_id, project_id). No plaintext token column, ever.
   - idempotency_keys: scope (user or credential id), request_id, request_hash, response jsonb, created_at; unique (scope, request_id). P1-C1/P1-D use this for the request_id convention in docs/api.md.
2. **Cross-project references are impossible at the database level, not just in code.** Use composite foreign keys, for example runs (agent_id, project_id) → agents (id, project_id), so that:
   - a run's agent is in the same project;
   - a run's parent run is in the same project;
   - a next step's source run is in the same project;
   - a credential's scoped project belongs to the credential's user.
   No ON DELETE CASCADE from projects, runs or users into history tables (PRD: retain history indefinitely; archive, don't delete). Indexes per the PRD: project/activity, project/status, run/event time, next-step completion, credential hash lookup.
3. **server/db/schema.ts**: Drizzle table definitions matching 0001 exactly. Add a test that introspects the migrated database (information_schema) and fails if any table or column in schema.ts differs from the real database in name, type or nullability. Drift between the two is the bug this prevents.
4. **server/repo/access.ts**: two access contexts:
   - `UserAccess {kind:'user', userId}` (browser session)
   - `CredentialAccess {kind:'credential', userId, credentialId, projectIds}` (MCP token, D-018)
5. **server/repo/**: repository modules for projects, agents, runs (+ events, PR refs, tool aggregates), next steps (+ waiting notes), private notes, audit events, credentials and idempotency keys. Every function takes an access context, and every query filters by it:
   - User access sees only projects whose owner_id = userId.
   - Credential access sees only its projectIds, and only if each belongs to the credential's user and the credential isn't revoked.
   - **Private-note functions accept only `UserAccess` at the type level**, so code that passes a `CredentialAccess` doesn't compile. Add a test that pins this, for example a `@ts-expect-error` line.
   - Writes that change an existing row take expected_revision and return a typed conflict carrying the current row on mismatch. Revision increments on every successful write.
   - Project lists support the active-first ordering and cursor pagination conventions in docs/api.md.
   This layer is data access only: no HTTP routes, no MCP tools, no password or token hashing logic. The credential repo stores and looks up a hash it is given.
6. **Tests** (server project, real Postgres via server/test/database.ts scratch databases) prove the properties, not just the happy path:
   - 0001 applies on an empty database; running the migrator again is a no-op; /ready reports current.
   - The schema-drift test from outcome 3.
   - Isolation: with two users A and B, every repo read and write that B attempts on A's data returns not-found or forbidden and changes nothing (row counts and revisions before and after).
   - Credential scope: a credential scoped to project X can't read or write project Y of the same user; a revoked credential can do nothing.
   - The database itself rejects cross-project references: a raw SQL insert of a run whose agent or parent is in another project fails on the constraint.
   - Revision conflict returns the current row and changes nothing.
   - Absent tool telemetry (no rows) stays distinguishable from a zero-count row.
   - The finished_at / execution_state check rejects inconsistent rows.

## The traps
1. **Isolation that lives only in the caller's good behaviour.** If a repo function takes a projectId and trusts it, P1-C1's MCP handler can be one missing check away from cross-account access. Every repo query must join or filter through the access context itself. Consequence of getting it wrong: one user's agent reads or writes another user's runs, which is the PRD's first acceptance scenario failing.
2. **Private notes reachable from an agent path.** A shared "project with everything" query that also pulls the note, or a notes function accepting any access kind, recreates the leak Phase 0 designed out (D-004). Keep notes in their own table, their own module, and a UserAccess-only signature.
3. **Owning auth tables.** Building sessions, accounts or invites now forces P1-B2 to rework them around better-auth. Stop at users.
4. **Schema/ORM drift.** Hand-written SQL plus hand-written Drizzle drift silently, and the bug shows up as a runtime error in another task. The introspection test is mandatory.
5. Fake timers vs systemClock and other web-side traps don't apply here. The database ones do: only create and drop your own uniquely named scratch databases (`supa_test_*` via the existing helper); never touch any other database.
