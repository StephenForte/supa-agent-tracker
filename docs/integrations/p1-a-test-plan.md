# P1-A2 operator client test script

Use the [dated matrix and source links](compat-matrix.md) as the documentary baseline. These steps are a future manual protocol, not executed results. P1-A1 only exercised an SDK client locally. Do not use Claude Code or an API as a substitute for Claude Desktop or Grok Bot. Deployment is a separate planner action with operator approval; [probe README](../../spike/mcp-probe/README.md) contains settings.

## Preparation and evidence rules

1. After the approved deployment, record actual `<PROBE_URL>` (HTTPS origin, no trailing slash), deployed commit, Node/SDK versions, UTC test time and operator. Generate `<PROBE_TOKEN>` privately; set it in Render and clients' credential fields only. Never paste it into chat, screenshots, PRs or reports. Warm `<PROBE_URL>/health`. This establishes the server baseline for R1–R3.
2. Use an otherwise empty project/chat and synthetic inputs. Record account tier, organization policy and client build per client (R9). Keep ordinary Chat and Cowork/unified mode results separate. Record exact UI availability, including negative evidence. “Control absent on this build/account” is narrower than “product never supports it.”
3. Keep one client active at a time. Read `/probe/log` after each stage using the README command; preserve the scrubbed JSON and UTC range privately. It includes calls from previous tests until 200 entries or restart. `initialize.clientInfo` and `probe_whoami` prove observed client metadata; a discovery GET alone does not prove an MCP connection. Empty logs may indicate reachability, cold-start or configuration failure, not lack of support.
4. Test bearer mode first, then an explicit authless control if it fails. The planner switches the same probe service to authless by unsetting `PROBE_TOKEN`, restarts, and notes log loss. Restore the secret after the control. This switch needs the same P1-A2 approval as deployment; never remove auth from a production tracker. No real accounts/data go through the probe.

## Cursor (C-test)

1. In Cursor editor record Help/About build, OS, account tier and whether this is a local session (R9). Use a synthetic project with Agent enabled. [Cursor MCP docs](https://cursor.com/docs/mcp) and [header setup](https://prod.cursor.com/help/customization/mcp), read 2026-10-15, describe the following config.
2. Add to your **personal** `~/.cursor/mcp.json` (merge with existing entries, do not overwrite other servers):

   ```json
   {
     "mcpServers": {
       "supa-mcp-probe": {
         "url": "<PROBE_URL>/mcp",
         "headers": { "Authorization": "Bearer <PROBE_TOKEN>" }
       }
     }
   }
   ```

   Replace placeholders locally; this credential-bearing file must not be committed. Restart Cursor as the setup docs direct, inspect MCP status/logs, and enable the three tools. Capture authenticated initialize or the actual failure (R1–R4). For the authless control remove `headers` and reconnect after the approved server switch: successful calls resolve the authless unknown in R3.
3. Ask: “Use the supa-mcp-probe tools. Call probe_whoami. Call probe_check_in with project_id='synthetic-p1-a2', agent_name='cursor-parent', title='Compatibility test', workload_type='coding'. Include harness and model only if your runtime supplies reliable identity; otherwise omit them. Retain its fake run_id and call probe_heartbeat once with that ID. Don't infer identity from your training or clientInfo.” Read `/probe/log`, verify all three calls and auth validity; record returned requested/negotiated versions (R1–R3). Compare model echo against selected model UI and, if available, minimal hook `model_id`; Auto is not an exact backend identity (R6).
4. Ask a **local** custom/general subagent to independently call whoami, check in as `cursor-child`, and heartbeat its own returned run. Use [documented subagents](https://cursor.com/docs/subagents), read 2026-10-15. Record tool access, permissions, child task card and correlated server timestamps. Child invocation may reuse the parent's clientInfo/session; server data alone cannot attribute it to a child. This validates R5 on this build. Cloud subagents are a separate team-configured path; don't use them to disprove local inheritance.
5. Remove the header while the server still requires a bearer. Record 401 → resource metadata → issuer metadata 501 if Cursor attempts OAuth. This fills only the discovery portion of R3. The probe cannot test DCR/PKCE/token exchange; leave OAuth 2.1+DCR unknown pending a planner-dispatched real authorization-server test. Restore header. This failure is expected, not a token to paste in an OAuth client-secret field.
6. For R7, first leave the active parent idle through two intended heartbeat intervals; read logs without reminding it. Then inspect [hooks](https://cursor.com/docs/hooks), read 2026-10-15. In a separate approved adapter experiment, capture only hook event/time/model ID and arrange a lifecycle-bound timer to call the MCP heartbeat using its own SDK connection and the exact active run ID. Do not install that adapter as part of this script automatically. Observe several intervals during a long tool and approval wait, then stop/cancel the parent and confirm timer termination. Event-only callbacks are not proof of periodic liveness. Until the adapter exists and passes, keep periodic R7 unknown.
7. For R8, run one harmless native file read and one harmless call to a different configured MCP. Compare minimal `postToolUse`/failure events against known actions. Don't collect raw tool arguments/output, secrets or transcripts. The probe log should contain neither other tool automatically. Record adapter coverage, child coverage and failures separately; model-reported totals do not qualify as captured telemetry.

## Claude Desktop on macOS (A-test)

1. Record Claude Desktop About build, macOS version, plan, organization role and Chat/Cowork/unified mode (R9). Use the remote connector flow, not a local `claude_desktop_config.json` stdio bridge. Current [setup instructions](https://claude.com/docs/connectors/custom/add-unlisted) and [Help Center](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), read 2026-10-15, describe the UI; the [auth reference](https://claude.com/docs/connectors/building/authentication) restricts static-header availability.
2. Open Customize → Connectors → + Add → Add custom connector. Organization Owners use Organization settings → Connectors. Enter name `supa-mcp-probe`, URL `<PROBE_URL>/mcp`, Continue; inspect detected auth. If Request headers is offered, select No sign in for this fixed-header test, add standard `authorization`, value `Bearer <PROBE_TOKEN>`, Required, and save. Do not add a second Authorization header alongside OAuth. Enable the connector via the chat “+” → Connectors. Capture whether the header UI exists for this account and successful authenticated calls (R1–R4). If absent, record it; follow the approved authless control with No sign in and no header. UI absence leaves the token path unverified; authless success confirms transport separately.
3. Use the C-test 3 prompt with `agent_name='claude-desktop-parent'` and appropriate workload. Verify whoami/check-in/heartbeat in the log. Compare any model echo to authoritative selection/runtime evidence; omission is correct when unknown (R6). Record tool approval prompts and reconnect behavior, not token values.
4. In Cowork or unified task mode, where [subagents are documented](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork), ask a child to independently run the three calls as `claude-desktop-child`. Record mode, child evidence and timestamps (R5). If ordinary Chat has no delegation, mark not available in that tested mode; do not borrow Claude Code's inheritance contract. A parent forwarding a call is not a successful child test.
5. Against bearer-required mode, try the normal Sign in flow with no fixed header. Expect 401 discovery and then the probe's explicit 501. Save discovery log entries (R3); stop there, with no account creation. Actual OAuth 2.1 compatibility, redirects and DCR/CIMD token acquisition require a later real OAuth fixture. A successful authless connection never fills OAuth support from live evidence.
6. For R7, leave the active run idle and during a long tool/approval wait; inspect whether heartbeat calls recur without reminders. Inspect available automation settings. [Scheduled Cowork tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork), read 2026-10-15, start their own sessions; they must not be used to keep an abandoned original run alive. A deterministic lifecycle-bound timer/hook must be demonstrated before recording guaranteed heartbeats. Do not create recurring paid model work for this check.
7. For R8 perform a harmless native/local tool action (if available in the recorded mode) and another connector call. Look for a documented export/adapter event stream and correlate it; screenshots and model memory do not prove complete telemetry. If no such API is available record “no capture surface found in tested mode,” leaving the broader unknown unresolved.

## Grok Bot (G-test)

1. Confirm this is the **Grok Bot at x.ai/bot**, not Grok's API or @grok on X. Record Support → About build, cloud computer software version if visible, plan and permissions (R9). [Settings](https://cursor.com/docs/grok-bot/settings), read 2026-10-15, says model selection is managed by the service.
2. Follow the documented [Connect plugins](https://cursor.com/help/grok-bot/connect-plugins) path: Connect apps in sidebar, browse/search, add, browser Authorize/Authenticate, confirm Installed. **The reviewed docs do not describe adding an arbitrary URL/header here.** Inspect whether this build exposes custom MCP or private-plugin configuration; record its actual labels. If it does, enter `<PROBE_URL>/mcp` and, only in a credential field, `Authorization: Bearer <PROBE_TOKEN>`. If it doesn't, stop this connection attempt and report the missing configuration surface. Do not assume local Cursor `mcp.json` controls Grok Bot. This is the live research needed for R1–R4; no invented installation instructions or new accounts.
3. If connected, run the same three-tool prompt as C-test 3 with `agent_name='grok-bot-parent'`, workload_type='automation'; verify log and requested/negotiated protocol, auth present/valid and clientInfo (R1–R3, R6). Leave model omitted without authoritative evidence. If the bearer path fails, use the approved authless control to distinguish missing transport from missing header support. Record inability to configure URL separately from transport rejection.
4. If delegation exists, ask a subagent to independently call the three tools as `grok-bot-child`; record child provenance (R5). Separately ask a second existing Bot on the same account to call them as `grok-bot-peer`; account-wide plugins are documented, but a peer Bot success does not prove subagent inheritance. Do not create or message other users' Bots. If no subagent surface exists, record that limitation.
5. If the custom connection has Sign in/OAuth, attempt discovery against bearer mode with no header; inspect log for the two discovery stages ending at 501. Do not label this a completed OAuth or DCR test (R3). If the UI supports only listed plugins, leave custom-MCP auth modes unknown and return the private-plugin/adapter gap to the planner.
6. For R7 inspect routines using [documented routine controls](https://cursor.com/help/grok-bot/routines), read 2026-10-15. Observe whether the existing active run independently emits heartbeats during idle/tool/approval waits. A routine schedule or inbound webhook starts work; it does not prove deterministic liveness of another run. Don't create paid recurring calls. Record lifecycle/timer API availability; leave unknown unless a reliable adapter actually exists and is tested.
7. For R8 perform one harmless native action and a separate plugin call. Inspect any supported event/export/hook API and compare coverage to these known actions; retain only aggregate/event metadata. The MCP probe cannot observe unrelated tool calls. If no capture surface exists, record that fact for this version without asserting product-wide absence.
